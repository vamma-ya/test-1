1. Архитектура решения

Я бы построил систему как набор специализированных агентов с единым оркестратором.

                    Руководитель
                         │
                         ▼
                 AI Orchestrator
                         │
          ┌──────────────┼──────────────┐
          ▼              ▼              ▼
     CRM Agent      Calls Agent    Analytics Agent
          │              │              │
          ▼              ▼              │
       amoCRM        Телефония           │
     сделки/задачи   записи звонков       │
          │              │                │
          │         STT → LLM             │
          │              │                │
          └──────────────┼────────────────┘
                         ▼
                  Report Generator
                         │
                         ▼
                Отчёт для руководителя


CRM Agent получает через REST API amoCRM сделки, задачи, статусы, ответственных и даты.

Calls Agent получает записи звонков из API телефонии. Аудио проходит через Speech-to-Text, после чего LLM анализирует транскрипции: причину обращения, результат звонка, возражения клиента, качество работы менеджера и следующие действия.

Analytics Agent объединяет данные CRM и телефонии и рассчитывает показатели отдела: количество сделок, просроченные задачи, активность менеджеров, результаты звонков, конверсию и проблемные места.

Report Generator формирует итоговый отчёт в понятном для руководителя виде: основные показатели, отклонения, проблемные сделки/менеджеры и рекомендации.

Результаты и промежуточные данные я бы хранил в PostgreSQL, а аудиозаписи — в объектном хранилище. Транскрипции и аналитические результаты можно дополнительно индексировать для поиска по звонкам.

2. Что система делает сама, а что передаёт человеку

Автоматически:

собирает данные из amoCRM и телефонии;

анализирует сделки, задачи и звонки;

определяет просроченные задачи и проблемные сделки;

анализирует качество разговоров;

находит повторяющиеся проблемы и отклонения;

формирует отчёт и рекомендации.

Человеку:

передаётся принятие важных управленческих решений;

спорные или недостаточно уверенные выводы;

действия, которые могут повлиять на клиента или сделку;

при необходимости руководитель может проверить исходный звонок и данные, на которых основан вывод.

Три главных риска:

Качество данных. Если менеджеры неаккуратно ведут CRM или часть звонков не записывается, аналитика будет неполной.

Ошибки AI. LLM может неправильно интерпретировать разговор, поэтому для важных решений нужен confidence score и возможность проверить исходные данные.

Конфиденциальность. Записи звонков и данные клиентов требуют правильного контроля доступа, хранения и обработки персональных данных.

3. Получение сделок без задач или с просроченными задачами

Для этого можно получить сделки через /api/v4/leads, а задачи через /api/v4/tasks. В API задач есть фильтры по entity_type, entity_id, is_completed и complete_till.

import os
import time
import requests

BASE = f"https://{os.environ['AMO_DOMAIN']}/api/v4"
HEADERS = {"Authorization": f"Bearer {os.environ['AMO_TOKEN']}"}

def get(path, params):
    r = requests.get(BASE + path, headers=HEADERS, params=params)
    r.raise_for_status()
    return r.json()["_embedded"]

# Берём открытые сделки
leads = get("/leads", {"limit": 250})["leads"]
ids = [lead["id"] for lead in leads]

# Все незавершённые задачи по сделкам
tasks = get("/tasks", {
    "limit": 250,
    "filter[entity_type]": "leads",
    "filter[is_completed]": 0
})["tasks"]

now = int(time.time())
tasks_by_lead = {}

for task in tasks:
    tasks_by_lead.setdefault(task["entity_id"], []).append(task)

result = []
for lead in leads:
    lead_tasks = tasks_by_lead.get(lead["id"], [])
    overdue = [
        t for t in lead_tasks
        if t.get("complete_till", 0) < now
    ]

    if not lead_tasks or overdue:
        result.append({
            "id": lead["id"],
            "name": lead["name"],
            "overdue_tasks": len(overdue)
        })

print(result)


В production-версии я бы добавил пагинацию, обработку rate limits и обновление данных по webhook, а не ограничивался одной страницей в 250 записей.

4. Реальный AI-проект

На предыдущем месте работы я участвовал в проекте по автоматизации первой линии технической поддержки с помощью голосового AI-агента.

Мы не стали сразу заменять сотрудников роботом. Сначала агент длительное время анализировал реальные разговоры операторов с клиентами: определял типовые вопросы, причины обращений и сценарии, которые можно безопасно автоматизировать.

После этого агент начали постепенно подключать к реальным звонкам. Он самостоятельно обрабатывал типовые обращения, а если не мог уверенно решить проблему или требовалось участие специалиста, быстро переводил разговор на человека.

В проекте использовались компоненты Voice AI: Speech-to-Text, LLM, Text-to-Speech, обработка телефонных звонков и логика эскалации.

5. Чему научился самостоятельно за последние полгода

За последние полгода я глубже погрузился в LLM и AI-агентов: научился строить системы, где модель не просто отвечает на вопрос, а получает данные из внешних систем, использует инструменты, анализирует информацию и выполняет последовательность действий.

Отдельно развивал навыки в Voice AI: Speech-to-Text, Text-to-Speech, анализе транскрипций и построении сценариев передачи диалога от AI человеку.

Практически это применил в проекте с голосовым агентом для технической поддержки. Благодаря этому я стал лучше понимать не только работу самой модели, но и то, как построить вокруг неё надёжную production-систему: интеграции, обработку ошибок, контроль действий и human-in-the-loop.

6. Пример самостоятельного улучшения

В процессе работы я заметил, что сотрудники технической поддержки тратят значительную часть времени на повторяющиеся обращения клиентов.

Изначально задача полностью автоматизировать этот процесс передо мной не стояла. Я сам предложил попробовать AI, но вместо идеи «сразу заменить операторов» предложил безопасный поэтапный вариант.

Сначала AI должен был анализировать реальные звонки сотрудников и выявлять типовые сценарии. Затем — подключаться к части обращений и работать вместе с человеком. И только после проверки качества — самостоятельно обрабатывать типовые вопросы с возможностью быстро перевести разговор специалисту.

Я проработал эту концепцию и довёл её до практического использования. В результате AI начал брать на себя рутинные обращения, а сотрудники смогли больше концентрироваться на сложных случаях.

Для меня это хороший пример инициативы: я сам заметил проблему, предложил не просто техническое решение, а изменение самого процесса, после чего довёл идею до работающего сценария.
